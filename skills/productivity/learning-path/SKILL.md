# Learning Path

Deliver a working static course with a roadmap, complete lesson pages and a cumulative practice project. The subject alone is enough to start. Use the requested destination or a fresh topic-named folder in the workspace.

## Choose the course language first

For a new course, ask in the user's language: “Which language should the course use: Arabic only, English only, or Arabic and English?” Wait for the answer before planning, copying the template or writing lessons. If the user already chose one of these in the request, use that answer. The language of the conversation alone does not select a course language.

Set `course.language` to `"ar"`, `"en"`, or `"both"` in the course copy. Write every teaching field, actor label and source label in the selected language(s). For example, a title can be `{ ar: "ترتيب القيم" }`, `{ en: "Sorting values" }`, or an object with both keys. Keep filenames, commands and API names as written. Only a course with both languages has a language menu.

When extending a course, keep its saved choice unless the user requests a change. Older copies used both languages. To change an older copy, update its bundled generator and validator from this template, keep its course data and lesson IDs, and apply the new choice to every lesson.

## Build from the original layout

Copy the contents of [assets/site](assets/site) into the course folder. Resolve that path relative to this SKILL.md. The copy is a self-contained site generator. For an existing course generated by this skill, edit its content in place. Preserve the supplied stylesheet, font requests, markup, diagrams and interactive shell. The navbar, search, level filters, table of contents, themes, copy buttons, quizzes and pagination are generated from course data.

Read [course.mjs](assets/site/course.mjs) for the complete working content example. Replace its sample course and section exports in the course copy. Large courses may import sections from local content modules. Use the chosen language(s) for the brand, learning journey, project setup and all teaching fields. Keep stable lesson IDs when extending a course. The number of lessons and sections follows the prerequisites and requested outcome.

## Design the learning path

1. Define the final capability as a demonstration the learner can perform. Use known experience as the starting point. For a Laravel developer familiar with CRUD, forms and MySQL, use those as bridges. Use an everyday analogy when it fits the topic better. Treat unfamiliar internals as new. If the user supplied a different background, use it.
2. Work backwards from that demonstration. Order sections from Junior to Mid-Level to Senior for a full track. Give each new tool, protocol or prerequisite its own introduction before a later lesson depends on it. Teach what it is, the problem it solves, basic terms, setup and a first observable result.
3. Use one practice project throughout. Inspect any supplied project before naming files, modules, commands or versions. For backend work, use the learner’s active practice repository from the workspace or conversation and its actual database, such as MySQL. For a different subject, choose a suitable project if none is given. Identify existing entry points and explicitly label modules the learner will build. Author exercises in the course. Change the practice repository only if requested.
4. Set a demonstrable project checkpoint at the end of each level taught. Each lesson must contribute a specific piece of that outcome.

## Write each lesson

- Open with a question whose answer the learner can observe. Use the purple callout for the bridge from familiar experience. From the second lesson onwards, set `previous` to text explaining how the *actual preceding lesson* leads here. Use the yellow callout for the mechanism that explains both outcomes.
- Create a controlled experiment. Keep the same three named actors, input and task in both cases. Change one condition, invite a prediction, then show what each actor observes. For an introduction, compare the problem without the concept to the same task with it. Put the intended outcome in case 1 (green diagram), the comparison in case 2 (red). Give each case an accurate filename and runnable code, commands or reproducible worked steps appropriate to the subject. Write the setup and how to run it in the introduction or mechanism. Keep diagram labels short enough to fit their boxes.
- Use plain English for English text and natural Egyptian Arabic for Arabic text. In a course with both, teach the same material in each. Put APIs, commands and paths inside backticks in prose. Use short actor labels and observations in actor order. The template uses them for the sequence diagram and comparison table.
- Give the lab a real scenario, a starting file or artifact, a concrete change, and a check the learner can run or observe. State the expected result. Include a concept-check question with plausible choices, one zero-based answer and a reason that explains the result. Prefer a fresh input that tests understanding.
- Open the official documentation for the target version before writing factual claims and link the relevant page in `source`. Verify project-specific claims against the checkout. Run runnable examples in an isolated practice context and distinguish observed outcomes from environment-dependent expectations.

## Build and verify

Run `node scripts/build.mjs` from the course copy. Resolve validation failures in its content, then check the generated lesson counts, first/previous/next links and checkpoint targets. Confirm no sample subject or project remains. Serve the course locally and inspect the overview and representative lessons in light and dark themes for each selected language. Check that a single-language course opens in the chosen language even with a different saved browser preference. For a course with both languages, switch between them on the same lesson. Check left-to-right English and right-to-left Arabic where enabled. Check diagram labels, mixed-direction text, Ctrl+K search, level filters, code copy and quiz feedback. Deliver the generated overview and its editable source together. Mention any verification that could not run.
